# AI Rules – Laravel E-commerce System

## Overview

Skill này chứa các quy tắc kiến trúc bắt buộc (MANDATORY) khi Antigravity phân tích và viết code cho hệ thống Laravel E-commerce hiện tại. Tất cả các tác vụ từ refactor đến thêm tính năng mới trong dự án đều phải tuân theo tài liệu này.

## Goal

Build a scalable, maintainable, and clean Laravel E-commerce system with architecture inspired by WooCommerce.

System must be:

- Extensible (dễ mở rộng)
- Maintainable (dễ bảo trì)
- Reusable (tái sử dụng cao)
- Clean & structured (code sạch, rõ ràng)

---

## AI Execution & Token Efficiency (Antigravity Support)

Để Antigravity (AI) hoạt động tối ưu, chính xác và tiết kiệm token nhất trong dự án này:

1. **Hiệu suất & Đọc file:**
    - Chỉ đọc (`view_file`) các file thật sự cần thiết.
    - Với file quá dài, dùng `grep_search` để tìm chính xác tên hàm, class cần sửa thay vì đọc toàn bộ nội dung.
    - Khi tìm hiểu context, hãy tham khảo các file gốc đã chuẩn theo kiến trúc (Ví dụ: `ShippingService.php`, `FlatRateDriver.php`) thay vì tự tạo lại pattern mới.

2. **Cập nhật & Chỉnh sửa (Write Code):**
    - RẤT QUAN TRỌNG: Hãy sử dụng công cụ vá lỗi cục bộ (`replace_file_content` hoặc `multi_replace_file_content`) để sửa một hàm hoặc một dòng nhất định. Tránh tuyệt đối việc overwrite (ghi đè) toàn bộ một file lớn nếu chỉ thay đổi vài dòng.
    - Không sinh thêm comment dư thừa, trừ khi giải thích một logic thật sự phức tạp. Không lặp lại các đoạn mã không thay đổi.

3. **Quy trình Thực thi:**
    - Tập trung vào vấn đề: Không thay đổi mã của các scope/tính năng không liên quan tới yêu cầu hiện tại.
    - Hồi đáp ngắn gọn (Lean Responses): Chỉ đưa ra kết quả, danh sách file thay đổi hoặc câu hỏi trực tiếp. Không cần sinh quá nhiều token để giải thích nếu user không yêu cầu.
    - Hỏi ý kiến (Ask Question): Nếu gặp trường hợp thiết kế không chắc chắn, phân định ranh giới Service/Action mập mờ, hãy mạnh dạn dừng lại hỏi user thay vì code "đoán" dẫn đến lãng phí token và thời gian rollback.

## Architecture

- Use Service Layer for all business logic
- Keep Controllers thin (only handle request/response)
- Do NOT put business logic in Models or Admin Resources
- Use Actions/Services for handling logic
- Follow OOP, SOLID, and Design Patterns

### Data Flow (STRICT)

**Controller / Resource → Service → Action → Model**

## Project Structure

- app/Services → business logic
- app/Actions → atomic logic
- app/DTOs → data transfer (optional)
- app/Enums → constants (status, type...)
- app/Models → data layer only

---

## Database

- Use snake_case for tables (shop_orders, shop_order_items)
- Do NOT rename existing tables
- Use migrations only (no direct DB edits)
- Schema must be extensible (support future features)

---

## 🗄️ Database & Migrations Rules (Development Phase)

- **NO SPAM MIGRATIONS:** Khi database chưa có dữ liệu thực tế (đang ở phase dev), **TUYỆT ĐỐI KHÔNG** tạo các file migration vụn vặt (VD: `add_column_*`, `drop_*`, `alter_*`).
- **DIRECT UPDATE:** Mọi thay đổi về Schema (thêm/sửa/xóa cột) bắt buộc phải được update trực tiếp vào file migration `create_*_table` gốc của bảng đó.
- **REBUILD DB:** Xóa các file migration lẻ tẻ nếu đã lỡ tạo. Sau khi sửa file gốc xong, luôn dùng lệnh `php artisan migrate:fresh --seed` để đập đi xây lại DB.
- **MỤC TIÊU:** Giữ cho thư mục `database/migrations` cực kỳ Clean, không bị rác rưởi bởi hàng chục file update lắt nhắt.

## Admin Rules

- Use Resource for CRUD only
- Resource = UI layer only
- No business logic inside Resource
- All data handling must go through Services

---

## Multilingual

- Use Spatie Translatable
- Fields like `name`, `description` stored as JSON
- Do NOT hardcode text
- Always use lang keys (trans())

---

## Code Style

- camelCase → variables, functions
- PascalCase → classes
- Clean, readable, self-explanatory code
- No duplicate logic
- Prefer reuse over rewrite
- Single Responsibility per function

---

## Coding Standards (STRICT)

- No inline business logic in Controller/Resource
- Each domain must have its own Service:
    - OrderService
    - ShippingService
    - TaxService
    - PaymentService

- No scattered DB queries
    - Centralize in Service/Repository

- No hardcode / magic values
- Clear variable naming
- Comment only when necessary

---

## Reusability (MANDATORY)

- Logic must be reusable across:
    - Admin (Laravel thu1ea7n)
    - API
    - Jobs / Background tasks

- Do NOT rewrite existing logic
- Extract shared logic into Services/Helpers

---

## Error Handling

- Use clear exceptions
- Do NOT silent fail
- Validate input using FormRequest or Validator classes

---

## WooCommerce-like System Design

### Separation of Concerns

- Orders
- Order Items
- Payments
- Addresses
- Shipping
- Tax

Each must be independent and modular

---

### Order System

- Order = snapshot (immutable data at time of purchase)
- Do NOT depend on Product data after order created
- Separate:
    - order_items
    - order_payments
    - order_addresses

- Always use DB transaction when creating/updating order

---

### Pricing System

Must be calculated via Service (NOT UI)

- Subtotal
- Tax
- Shipping
- Discount (extensible)
- Total

Use centralized calculator (e.g. OrderCalculatorService)

---

### Shipping System

- Support flexible rules:
    - country
    - state (optional)
    - postcode (optional)

- Matching logic must be reusable
- External API for address (no hardcoded city/state/ward)

---

### Tax System

- Tax rules must support:
    - country
    - state
    - postcode
- Tax must be read-only in order detail

---

### Payment System

- Pluggable architecture
- Easy to add new providers
- Separate logic from Order

---

## UI/UX Rules

- Follow WooCommerce UX where possible
- Group related features logically
- Use dropdowns instead of cluttered actions
- Settings page must use tabs:
    - General
    - Tax
    - Shipping

---

## Maintainability

- Code must be:
    - Easy to read
    - Easy to refactor
    - Easy for new developers

- No hidden logic
- No tight coupling

---

## Important (STRICT)

- Do NOT break existing structure
- Always follow current project patterns
- Do NOT quick fix → always design properly
- Always think:
    - Can this scale?
    - Can this be reused?
    - Is this clean?

---

## Expected Outcome

- Clean, modular codebase
- WooCommerce-like architecture adapted for Laravel
- Easy to scale (multi-country, multi-tax, multi-shipping)
- Can evolve into a long-term product/plugin
